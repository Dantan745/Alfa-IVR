# База Alfa Кошелёк ЦР — для Стёпы

Стёпа, боевые данные лежат в PostgreSQL, не в файле. Сервер сам создаёт таблицы при старте из строки `SCHEMA` в `server/db.mjs`. Отдельной папки миграций нет: новые столбцы добавляются там же через `ADD COLUMN IF NOT EXISTS`.

Формальная модель в третьей нормальной форме, со связями и зависимостями: `docs/relational-model.md`. Этот файл — как база живёт в продукте.

Живой сайт: https://alfa-koshelek-cr.fly.dev . Кластер называется `alfa-koshelek-db`, регион `fra`. Строка подключения — секрет `DATABASE_URL` у приложения `alfa-koshelek-cr`. В репозиторий её не кладём.

Локально, если PostgreSQL ещё не поднят в проде на твоей машине, `docker-compose.yml` поднимает Postgres 16: пользователь `alfa`, база `alfa`, пароль `alfa`, порт 5432. Без `DATABASE_URL` и без `NODE_ENV=production` сервер сам берёт `postgresql://alfa:alfa@127.0.0.1:5432/alfa`. В проде без `DATABASE_URL` процесс не стартует.

## Что в таблицах

Имя клиента — `app_user`, потому что слово `user` в PostgreSQL занято. Ключ — `email`. Телефон и номер кошелька уникальны. `phone_key` — вычисляемые последние 10 цифр номера, по ним ищется человек.

`wallet` — один кошелёк на email: баланс, PIN, лимиты и пороги предупреждений. Деньги — `numeric(14,2)`. Время везде — `bigint`, миллисекунды Unix, не `timestamptz`.

`savings` — копилки, потому что их может быть несколько. `user_device` — устройства входа. `session` — сессии на 14 дней. `otp_code` — одноразовый код. У этой таблицы нет внешнего ключа на клиента: код регистрации пишется раньше, чем появляется строка пользователя.

`tx` — операции. `linked_tx_id` связывает списание и зачисление одного перевода. `tx_mark` — ответ модели по уже записанной операции: `anomaly` (0 или 1) и `final_score`. Набор признаков в эту таблицу не входит.

`note` — уведомления, `contact` — адресная книга владельца, `audit_log` — журнал действий кабинета, `notify_settings` — одна строка настроек почты и бота, `telegram_link` — последние 10 цифр телефона и чат Telegram, куда слать код. У `telegram_link` нет внешнего ключа: номер можно привязать до регистрации.

## Хеши

Пароль и PIN не хранятся текстом. Формат пароля — scrypt с солью: `scrypt$N$r$p$соль$ключ` (`server/passwords.mjs`). Старые записи `sha256$…` ещё проверяются и при успешном входе заменяются на scrypt.

Токен сессии в таблице — SHA-256 от выданного клиенту значения. Код из Telegram или письма в `otp_code.code` — тоже SHA-256, не шесть цифр. Сравнение идёт через `timingSafeEqual`.

Секрет бота и пароль SMTP в ответах API не возвращаются.

## Как пишутся деньги

Пул соединений `pg`, максимум 10. Транзакция — `withTx` через `AsyncLocalStorage`. Вложенный вызов присоединяется к уже открытой транзакции и не делает второй `BEGIN`.

Перевод, QR и одна строка массового платежа списывают и зачисляют внутри одной такой транзакции. Скоринг Python вызывается до неё, чтобы ожидание модели не держало блокировку строки.

Пустая база один раз забирает старый `server/data.json`, если файл есть, и хеширует пароли при переносе. Файл после этого остаётся резервной копией и в git не коммитится. Туда же нельзя класть `.env`, `notify.json` и секреты.

## Что можно менять спокойно

Схему правь в `SCHEMA` внутри `server/db.mjs` и так, чтобы повторный запуск на уже живой базе не падал: `IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, снятие ограничения перед новым. После правки обнови `docs/relational-model.md`, чтобы описание не разъехалось с сервером.

Не меняй `server/ml/anti_fraud.joblib` и `server/ml/anti_fraud_infer.py`: это файлы Дани.
